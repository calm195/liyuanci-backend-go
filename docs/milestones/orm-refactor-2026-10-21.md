# ORM 实体与自动迁移重构（2026-10-21）

承接 T005/T008、REQ-018/020。用户授权新建 `codex/gorm-entity-refactor` 分支，要求每张实体表对应结构体、遵循 GORM 建模方式、减少手写 ORM SQL、启用自动迁移，并要求按功能模块分文件存储。本次授权替代此前全面禁止 AutoMigrate 的约定；不涉及提交、推送或部署。

## 实现范围与模块职责

`internal/entity` 提供 46 张现有表的一对一结构体映射，包括 public 业务表、evidence 隔离域、业务/恢复迁移账本、独立恢复日志与集成探针。文件按账号、身份、后台、会话、互动、审核、持久工作、证据、恢复、探针和迁移账本拆分，`registry.go` 单独维护业务迁移注册表。所有字段显式声明数据库类型和中文注释，显式表名包含 schema，主键及复合主键保持原结构；可空标量使用指针，JSONB 使用 `json.RawMessage`，敏感实体不直接序列化成 API JSON。

没有嵌入 `gorm.Model`：原表使用 UUID/复合主键、数据库时间及物理清理，不能附带引入 uint 自增主键、更新时间或软删除列。`CreatedAt` 关闭 GORM 自动赋时并声明数据库默认值；会话生成列与恢复日志 identity 序号只读，不参与普通字段迁移。实体不添加隐式关联级联保存，聚合及跨表事务仍由领域服务负责。

后台账号/角色/会话/留迹创建、账号查询、改密和会话撤销、角色删除和批量插入、版本原子递增、幂等回执冲突更新，以及学生会话创建、交换回执读取/行锁/完成、唯一交换领取、本人资料更新和会话撤销改用 GORM 的 Model/Create/Updates/Delete/Clauses。更新 `false` 等零值使用显式 map；数据库版本递增与交换期限使用 GORM 表达式，保持 PostgreSQL 原子性和数据库时钟。服务及命令边界继续通过注入的 zap 日志器记录 request_id、result、duration；仓储不重复输出敏感参数。

## 自动迁移关键流程

业务入口仍为显式 `go run ./cmd/migrate up`（或构建的 migrate 二进制），依次获取 PostgreSQL 事务级技术锁、验证独立库边界及历史文件校验和、应用待执行版本 SQL、调用 `AutoMigrate(entity.BusinessModels()...)`、提交事务。已处于最新版本时也执行实体同步，自动补齐缺失的常规字段。失败回滚整个批次，原有结构化完成日志记录失败。历史 SQL 文件与版本校验和没有改写。

`journal-up` 在独立恢复库完成版本结构后，仅自动迁移恢复账本与恢复日志实体；恢复库与业务库不能混建。探针仅有结构体映射，保持隔离探针迁移入口，不自动加入业务迁移。

API/worker 普通启动不执行 DDL，使用受限运行账号；AutoMigrate 由显式迁移入口使用迁移身份执行。PostgreSQL 专用生成列、RLS、DEFERRABLE 外键、部分/复合索引、CHECK、数据库函数与权限矩阵仍由版本 SQL 提供。这些机制不能由常规字段映射完整替代。GORM 自动迁移不是删列或重命名工具；新增实体表仍需相应版本 SQL 提供中文表注释、专用约束和权限。首批不删除已有专用 SQL，也不重构命令锁函数、恢复补偿和领域复杂查询的 SQL；后续普通 CRUD 统一范围见下方增量。

实现依据：[GORM 模型声明](https://gorm.io/docs/models.html)、[自动迁移](https://gorm.io/docs/migration.html)。实体映射测试逐项核对迁移中的字段注释所列数据库列，并检查唯一表映射、主键、中文字段注释、只读生成列及恢复/探针不混入业务注册表。

## 后续模块 ORM 统一增量

T004–T008、REQ-018/020：承接用户要求，将身份存储、事务命令、持久工作、迁移账本及探针中的常规增删改查统一到现有实体与 GORM，不新增依赖、不变更数据表或历史 SQL 校验和。认证模块剩余的常规投影、权限计数和后台分页也改为实体查询。

- 身份模块使用实体创建账号、JSONB 密文与检索占用，通过 `OnConflict` 保持用途配置的幂等初始化；检索代次更新、旧占用删除及密文重写采用实体更新。回填与完成轮换共享实体子查询的 `NOT EXISTS` 缺口判定，回填的有界分页与行锁保持不变；JSONB 的 KeyRef 提取和 `IS DISTINCT FROM` 保留为 PostgreSQL 谓词。
- 命令模块使用实体进行只读会话联表发现、排序资源行锁、锁后会话/角色读取与惩罚计数。幂等回执使用 GORM `OnConflict`，冲突更新仍只允许覆盖数据库中已到期的回执，零行仍触发原有重试，业务结果与回执仍由根事务一起提交。
- 持久工作模块使用实体进行工作行锁、消费回执计数和创建、终态/重试/租约清理、旧事件替代与新事件创建。计数和版本通过数据库表达式递增，NULL 和零次数使用显式 map 写入，所有失败和恢复仍由既有注入日志器在拥有事务的边界记录完成结果。
- 业务与恢复迁移账本使用实体读取、创建和删除；DDL、对象注释、版本 SQL、权限配置和迁移技术锁仍保留专用入口。探针消费者使用实体和 `OnConflict` 原子累加投递计数，生产探针通过实体读取消费计数；数据库写入成功后才确认消息。
- 后台/学生查询改为实体投影与 GORM 行锁/计数；后台列表保留 PostgreSQL JSON 聚合表达式以获取单次角色快照，分页、游标及过滤交由 GORM。普通联表仍是单次查询，没有拆成跨快照的多次读取。

### 必要的 PostgreSQL 专用逻辑

保留事务级 advisory lock、受控账号/后台锁函数、事务内 lock_timeout、clock_timestamp/interval、JSONB 与数据库目录权限检查；这些没有对应的可替代业务内存逻辑。持久工作与事件的单语句写入 CTE 保证调用方误忽略错误时也不只写入半份工作；队列候选的 `FOR UPDATE OF ... SKIP LOCKED` 和租约 `UPDATE ... RETURNING` 保持领取锁序与原子快照；补偿及重驱动的 LATERAL 最新有效事件关联和原子 NOT EXISTS 条件更新保留。没有为了减少 SQL 行数而拆开上述并发控制语句。

### 兼容问题与真实验证

真实隔离测试发现并修正了两处 GORM 行为差异：工作 DTO 包含仅在联表时存在的 `target_version`，直接让 GORM 推断投影会查询不存在的源表列，锁源表时已显式选择真实列；后台消费回执仅允许读取键，GORM 默认回读 `completed_at` 会触发列权限拒绝，现通过 `Returning` 只回读已授权的 operation_id。数据库权限矩阵没有放宽。现有真实权限测试保留了拒绝读取完成时间和拒绝修改消费回执的断言，并强化身份各事务操作成功耗时、消费成功与失败完成日志断言。
